# issue #45：开仓被后台同步挡住

## 现场查到的原因

读取了线上容器的版本、健康状态、任务接口、只读 SQLite 和轮转请求日志。线上版本是 `5b7aeb5a48e2c4e44a131d40b6246848558738e8`。未改交易数据、未手动开仓、未补跑失败时段。

以下时间全部是 **UTC**，不是浏览器或本机时区。

| 开仓计划时间 | 数据库结果 | 同时在做什么 |
| --- | --- | --- |
| 2026-10-30 13:00 | completed | 同步在 13:00:00.291 完成，开仓随后正常执行 |
| 2026-10-31 13:00 | failed，13:00:00.261 结束 | 订单同步的分页请求持续到 13:00:00.882 |
| 2026-11-01 13:00 | failed，13:00:00.198 结束 | 订单同步的合约、分页请求持续到 13:00:00.998 |

这两天的后台订单同步在开仓前几秒开始，跨过整点，占着 Gate 状态。开仓在真正交易前被拒绝。由于每天只开仓一次，界面一直保留上次失败信息，看上去像“卡了两天”。排查时所有任务已空闲，之后每分钟订单同步仍能成功，不能把它说成同一个任务卡住两天。

## 修改后的行为

- 每分钟后台订单同步，在下次自动开仓前 60 秒及该时段尚未被处理时让路；调度正在处理任务时也不再启动后台同步。开仓处理后恢复正常轮询。手动刷新仍可执行。
- 遇到确实在运行的来源刷新、订单同步、开仓、持仓维护或人工核对，仍然返回 409 跳过。提示列出占用任务的中文名称、任务代号和已运行秒数；同时占用时全部列出。
- 不排队，不补跑过去时段，不把网络失败的交易自动重发。用户已明确选择保留跳过行为。
- 来源刷新和各 Gate 任务共用同一种生命周期管理，连接获取后的初始化也放在 `try/finally` 内；成功、失败、初始化异常都释放任务状态和连接占用。
- 一个 HTTP 请求从发送到响应体读完，最多 30 秒；即使注入的传输不响应取消，调用方也能结束等待。失败时取消响应体，清理计时器和监听器；不等待可能卡住的 `cancel()`。迟到的响应只清理，不恢复业务调用。
- 同一业务任务的所有分页、合约查询、交易请求共用 300 秒预算，避免“每页都不到 30 秒，整批却运行很久”。到期取消当前 I/O，后续请求检查已取消状态，沿原调用链退出后才释放状态，不用外层抢先解锁的方式留下后台交易。
- 交易写入超时仍交给已有交易意图机制，保存为 `unknown`，后续写入必须先人工核对。一次批量操作已确认成功的早期交易不会被撤回。
- 出站请求日志增加 `task` 字段，便于把任务占用与网络请求对上；不记录密钥、请求体或查询字符串。

60 秒让路窗口处理了现场的每分钟轮询撞车。若更早开始的长任务、手动刷新或人工核对仍跨过开仓时刻，仍按用户选择跳过并报告实际占用，不保证所有任务竞争下都能开仓。300 秒预算是网络工作流的边界；事件循环被同步代码或系统阻塞时，计时器不能强制抢占。
